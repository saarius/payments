# Backroad Bum private Payments host

Merchant-only Node 24 operations code on `saarius/payments:backroadbum/test-runtime`, based on the same v0.5.0 source as the installed Registry plugin. It composes Payments' existing Checkout Session, provider, authentication and HTTP ports with durable SQLite claims; Commerce still owns prices, checkout snapshots, attempts, orders and receipts. This is not a new package entry point, upstream proposal, or replacement Registry plugin.

`runtime.mjs` listens only on `127.0.0.1:8787`. It rejects non-test keys and verifies that the key belongs to the configured own-account sandbox before listening or admitting a new session. This is not connected-account readiness: the actual sandbox accepted an unpaid TEST session while its v1 `charges_enabled` flag was false. Stripe documents sandbox use before live activation at https://docs.stripe.com/get-started/account/activate. A private ES256 issuer binds five-minute passes to this single merchant, site, origin, audience and scope; immutable binding metadata and attempts survive restart. HTTP 5xx responses never include processor exception text.

## Operator setup

On this host only, install dependencies on Node 24, run `sudo node ops/backroadbum/configure.mjs` once, and create `/var/lib/backroadbum/payments` owned by `agent`, mode 0700. The bootstrap creates `/etc/backroadbum/payments.json` with mode 0600 and refuses to replace an existing file. Stripe credentials remain in the operator-managed `/etc/backroadbum/stripe.env`; do not copy them into the repository or change that file.

Install the supplied systemd unit, reload systemd, and enable `backroadbum-payments.service`. Run `node --import tsx --test tests/backroadbum-runtime.test.mjs` for the focused tests. `check.mjs` is a read-only authenticated check. With the private test environment loaded, `diagnose-account.mjs` emits only redacted readiness facts; `probe-checkout.mjs --run` explicitly creates one unpaid $1 TEST session through Payments, retrieves it, and immediately expires it. The probe has no card input and is not a Commerce order or paid-order proof. No package publication or shared DinkusKit service deployment is involved.

## Merchant integration and webhook delivery

The merchant Commerce profile fetches `/api/commerce-settings` using its separate `commerce:settings` audience and exchanges Payments passes on this merchant's exact host. Cross-audience or cross-scope passes are refused; the settings response contains no credential. Guest-browser Stripe TEST checkout, pending recovery and paid receipts are proven privately. The generic Commerce build still uses its fixed DinkusKit.com trust boundary.

The existing own-account TEST endpoint `/v1/webhooks/stripe` verifies the original bytes with the operator-provided `STRIPE_WEBHOOK_SECRET`. The merchant adapter accepts only direct `checkout.session.completed` events with no `event.account`, verifies the API key's current account, and independently retrieves the same event ID in that own-account context; relevant signed identity fields must match. It never synthesizes `event.account` or weakens the generic Connect matcher. Existing Payments session/amount/window matching must succeed before an immutable event-keyed wake is durably inserted in `attempts.db`.

`GET /v1/checkout/wakes` and `POST /v1/checkout/wakes/ack` use existing scoped, merchant/site-bound passes. A wake contains only event/attempt/binding IDs, generation and time; ACK compares the complete tuple, and provider redelivery never resurrects an acknowledged event. Commerce's existing five-minute task does authoritative provider reconciliation and acknowledges only its canonical terminal result. On November10, a new TEST payment became order #1003 through this path with its browser return and post-payment status calls blocked.

`node --import tsx --test tests/backroadbum-runtime.test.mjs tests/backroadbum-webhooks.test.mjs` verifies the composition. With the private test environment loaded without echoing it, `node --import tsx ops/backroadbum/replay-webhook.mjs --check` inspects the retained shopper proof; `--resend` explicitly asks Stripe to redeliver its real event (same API operation as Stripe CLI). Optional `--state-file=/etc/backroadbum/webhook-shopper-browser.json` selects the later background-order proof. These commands create no session/payment/order and never sign a fabricated delivery themselves.

There are no Sales, catalog, cart, order or receipt tables in this runtime. Public TEST checkout is open behind independent admission controls; Ship fulfillment, account/email recovery and off-host recovery remain unfinished.

## Separate merchant Ship admin grant

This host also serves the merchant issuer; `ship-grant.mjs` is a merchant extension, not a Payments product API. `sudo node ops/backroadbum/configure-ship-grant.mjs` creates `/etc/backroadbum/ship-grant.json`0600 with a separate random plugin key and `enabled:false`, preserving any existing grant. Give `agent` read access without widening the mode. Provision only Ship's encrypted `connection` setting through the store's authenticated API, then deliberately enable this grant. No signing key, Payments binding, Stripe environment or Commerce setting changes.

The issuer reads the file on each exchange, refusing missing, malformed, linked, oversized, permissive or disabled files for Ship while existing Payments/Commerce exchanges continue. The fixed `/.well-known/jwks.json` route exposes only the existing ES256 public verification key, with the same `kid` used to sign passes; no private component or alternate key selection is returned. The Ship key grants only the fixed `ship:admin` scope and `backroadbum-ship` audience for the exact merchant site/origin; it cannot mint machine `ship:orders`, Payments or Commerce settings passes. The Commerce key still cannot mint Ship admin passes; its separate machine grant is described below. Ship orders/labels remain in Ship; the Payments database holds only the merchant issuer’s bounded admission configuration. Focused proof: `node --import tsx --test tests/backroadbum-ship-grant.test.mjs tests/backroadbum-runtime.test.mjs`.

Disabling or rotating the private grant affects the next exchange. Ship’s native page trades on every load and action, without KV caching; its current merchant profile can save a demo origin and boxes under `ship:admin`, while intake remains closed. Already-issued passes remain valid for at most five minutes; remove the exact Ship proxy import for immediate cutoff. The grant is not in the narrow SQLite/Ship-print backup; retain its recovery separately before widening integration. It does not admit orders or authorize postage. `node ops/backroadbum/check-ship-grant.mjs` verifies the real public JWKS signature, issuer/receiver binding, cross-grant denials and GET status/orders proxy without effects; `--expect-disabled` verifies a disabled grant. It emits only allowlisted summary facts, never response bodies or tokens.

## Bounded Commerce machine admission

`commerce-ship.mjs` owns one `merchant_ship_admission` configuration row in the existing private `payments/attempts.db`, not a second order model. `node ops/backroadbum/configure-commerce-ship.mjs` initializes only revision0/unselected/disabled state, after checking the existing Payments database binding and private dynamic Ship generation. It never overwrites a selected ID, freshness cutoff or corrupt/missing row. Production remains in this initial state.

The synchronous control helper requires current revision, orderId and enabled fields. The original generation/cutoff are immutable; once chosen, an ID cannot change or clear, including across disable/re-enable and restart. There is no HTTP/native selector or enable action. A future operator workflow must establish one deliberately fresh provider-paid canonical TEST order before calling this control and coordinating Ship’s separate admission. Do not edit rows, reset generations or adopt fixtures/historical orders.

GET `/api/commerce-ship` requires the existing exact-site/origin `commerce:settings` pass and returns only this configuration. The row and private Ship generation are reread for every response and machine-pass exchange. Missing/corrupt/mismatched state returns unavailable for Ship without breaking payment grants. Only while enabled can Commerce’s existing key trade a five-minute `ship:orders` pass for audience `backroadbum-ship`; it never gains `ship:admin`. Ship’s separate key remains admin-only and cannot read this configuration or call Payments. The normal checkout settings response still has no `ship` object.

Commerce’s merchant-v2 adapter rechecks current admission before dispatch/CAS/ACK rather than relying on pass expiry. Disable therefore stops later work even with an already-issued machine pass; previously dispatched calls may drain. Restoring a matching recorded completion can recover a lost ACK on same-order re-enable. Tests: `node --import tsx --test tests/backroadbum-commerce-ship.test.mjs tests/backroadbum-ship-grant.test.mjs tests/backroadbum-runtime.test.mjs tests/backroadbum-webhooks.test.mjs`.

The normal site backup includes a consistent copy of `payments/attempts.db`, including this durable admission row. Each database is copied consistently, not as one cross-service transaction; restore with both Commerce/Ship admissions disabled and reconcile canonical order/provider/event state before re-enabling. Never reset a pinned row or replay a stale enabled snapshot blindly. Secrets require separate operator recovery and must never enter a public artifact. Local snapshots alone are not off-host recovery.
